# Documentation standards

## Objetivo

Definir cómo debe mantenerse la documentación de MUBER 2.

## Regla general

La documentación debe ayudar a:
- entender el sistema
- operar el piloto
- implementar sin perder contexto
- verificar cambios
- alinear GitHub y Notion

## Dónde vive cada cosa

### `README.md`
Contexto general del proyecto.

### `docs/`
Documentación técnica y operativa.

### `ai-specs/specs/`
Reglas y estándares del proyecto.

### `openspec/specs/`
Specs vivas por dominio.

### `openspec/changes/`
Cambios abiertos, propuestas, tareas y diseño.

### Notion
Centro operativo, dashboard, métricas y documentación ejecutiva.

## Regla de actualización

Cuando una mejora cambie:
- flujo
- datos
- estados
- pantalla
- operación

también debe evaluarse si hay que actualizar documentación.

## Regla de claridad

La documentación debe ser:
- específica
- simple
- útil
- fácil de revisar

No debe ser:
- genérica
- inflada
- decorativa
- repetitiva sin motivo

## Regla de no pérdida

Las decisiones importantes no deben quedar solo en conversación.
Deben quedar registradas en el sistema documental.

## Regla final

Si el proyecto avanza pero la documentación queda atrás, el sistema se desordena.
En MUBER 2, documentación y ejecución deben avanzar juntas.
