# Análisis del cuestionario de usuarios vs realidad actual de MUBER

## Propósito

Este documento analiza las respuestas disponibles del cuestionario de investigación de usuarios para el prototipo de app de mudanzas MUBER y las contrasta con el estado actual del proyecto MUBER 3 / MUBER 2.

El objetivo es usar investigación existente como insumo directo para la última iteración antes del piloto real/comercial.

## Fuente analizada

Documento base:

```text
Cuestionario de Investigación de Usuarios para Prototipo de App de Mudanzas (Muber) (respuestas)
```

Ubicación:

```text
Google Drive / Google Sheets
```

Hoja:

```text
Respuestas de formulario 1
```

Datos visibles analizados:

```text
8 respuestas con contenido completo o parcial
20 columnas de preguntas principales visibles
```

Nota metodológica:

```text
La muestra es pequeña y exploratoria. No debe usarse todavía como prueba estadística concluyente. Sí sirve para detectar patrones tempranos, hipótesis y prioridades de validación antes del piloto.
```

## Variables analizadas

El cuestionario contiene preguntas sobre:

```text
- frecuencia de mudanza
- razones para usar una app de mudanzas
- nivel de estrés en la última mudanza
- importancia del precio
- reputación y reseñas
- seguro
- personalización del servicio
- preferencia por teléfono/email versus app
- tipo de mudanza
- parte del proceso que se desea simplificar
- calculadora de volumen / inventario
- chat directo con proveedor
- pagos integrados
- calendario y recordatorios
- seguimiento GPS en tiempo real
- fecha aproximada de próxima mudanza
- tiempo dedicado a comparar empresas
- probabilidad de usar valoración del proveedor
```

# 2. Principales hallazgos del cuestionario

## 2.1 Estrés de la mudanza

Respuestas visibles sobre estrés:

```text
5, 10, 5, 9, 8, 10, 8, 8
```

Lectura:

```text
- 6 de 8 respuestas están en 8 o más
- 2 de 8 respuestas están en 5
```

Conclusión:

```text
La mudanza aparece como un proceso de alto estrés para la mayoría de la muestra visible.
```

Implicación para MUBER:

```text
La promesa “mudanza sin estrés” está bien alineada con la realidad inicial detectada.
```

Prioridad de producto:

```text
MUBER debe reducir ansiedad, no solo transportar objetos.
```

---

## 2.2 Razones para usar una app

Motivadores detectados:

```text
- comodidad y rapidez para cotizar
- comparar precios y servicios fácilmente
- seguimiento en tiempo real
- contratación de servicios adicionales
- necesidad de organizar inventario
```

Patrón dominante:

```text
Cotizar rápido + comparar precios aparecen como motivadores recurrentes.
```

Patrón secundario:

```text
Tracking/GPS aparece como reductor de incertidumbre.
```

Implicación para MUBER:

```text
El usuario no está pidiendo solo una app bonita. Está pidiendo claridad, precio, comparación y seguimiento.
```

---

## 2.3 Precio

La afirmación “el precio es el factor más importante” tuvo respuestas mixtas:

```text
- totalmente de acuerdo / de acuerdo en varias respuestas
- neutral en una
- en desacuerdo o totalmente en desacuerdo en algunas
```

Lectura:

```text
El precio importa, pero no es el único factor. Seguridad, reputación, GPS, pagos y claridad también pesan.
```

Implicación para MUBER:

```text
No conviene competir solo como “el más barato”. Conviene competir como precio claro, justo y sin sorpresas.
```

Mensaje sugerido:

```text
Precio claro antes de confirmar. Sin sorpresas.
```

---

## 2.4 Reputación y reseñas

Varias respuestas valoran reputación/reseñas como importantes:

```text
- de acuerdo
- totalmente de acuerdo
```

Aunque hay respuestas en desacuerdo, el patrón general sugiere que la confianza del proveedor importa.

Implicación para MUBER:

```text
El sistema de rating, reseñas y validación de choferes debe ser visible, no solo interno.
```

MUBER hoy:

```text
El flujo Driver ya muestra rating y bono 10%, pero falta cerrar mejor cómo ve el usuario la confianza del chofer desde User/Assisted.
```

---

## 2.5 Seguro y respaldo

La disponibilidad de seguro aparece con respuestas mixtas:

```text
- de acuerdo
- neutral
- totalmente en desacuerdo en algunos casos
```

Lectura:

```text
No todos lo mencionan como indispensable, pero en una mudanza real el daño/pérdida de objetos puede transformarse en barrera crítica.
```

Implicación:

```text
MUBER debe validar en la próxima investigación cuánto pesa realmente el respaldo/garantía/seguro antes de pedir pago o confirmar viaje.
```

---

## 2.6 Personalización del servicio

La personalización aparece como relevante:

```text
- solo transporte
- servicios adicionales
- embalaje
- desmontaje
- inventario
```

Implicación:

```text
MUBER debe mantener los flujos diferenciados: User, Assisted, Driver y servicios adicionales.
```

MUBER hoy:

```text
El flujo Assisted y el inventario son coherentes con esta necesidad, pero deben validarse en test de guerrilla porque pueden generar fricción si son largos.
```

---

## 2.7 Preferencia teléfono/email versus app

Hay respuestas mixtas:

```text
- algunos prefieren teléfono/email
- otros no
- algunos neutral
```

Lectura:

```text
Hay una tensión real: parte de los usuarios quiere autoservicio digital, pero parte necesita contacto humano o canal tradicional.
```

Implicación para MUBER:

```text
La idea inicial de chat híbrido / asesor humano sigue siendo válida.
```

MUBER hoy:

```text
La app tiene flujos digitales, pero todavía no se ve consolidado un canal humano claro integrado al proceso.
```

Prioridad:

```text
Definir si el soporte humano inicial será WhatsApp, llamada, chat simple o botón de contacto asistido.
```

---

## 2.8 Tipo de mudanza

Predominan:

```text
- casa de 3 o más habitaciones
- apartamento pequeño 1-2 habitaciones
```

Lectura:

```text
La muestra mezcla mudanzas grandes y pequeñas. Esto puede generar necesidades distintas.
```

Implicación:

```text
MUBER debe separar claramente tipos de servicio:
- última milla / flete pequeño
- mudanza pequeña
- mudanza asistida
- mudanza mayor / cotización especial
```

MUBER hoy:

```text
El producto ya está avanzando hacia flujos diferenciados, pero debe quedar muy claro para el usuario desde el inicio qué tipo de servicio está pidiendo.
```

---

## 2.9 Parte del proceso que quieren simplificar

Respuestas abiertas detectadas:

```text
- seguridad
- costo según distancias
- precio
- embalaje
- una que me dé lo que busco
- no me interesan las aplicaciones
```

Lectura:

```text
El usuario no piensa en términos de funcionalidades técnicas. Piensa en dolor: seguridad, precio, embalaje, claridad y utilidad real.
```

Implicación:

```text
El lenguaje de MUBER debe hablar menos de “flujo” o “tracking” y más de resolver problemas concretos.
```

Ejemplos de copy:

```text
- Calcula el costo antes de pedir el servicio.
- Agrega tus objetos sin complicarte.
- Sigue tu traslado en tiempo real.
- Pide ayuda si necesitas embalaje o asistencia.
```

---

## 2.10 Inventario / calculadora de volumen

Las respuestas son variables:

```text
- esencial
- muy importante
- moderadamente importante
- poco importante
- no importante
```

Lectura:

```text
El inventario es diferenciador, pero no todos los usuarios lo valoran igual.
```

Implicación:

```text
El inventario no debe bloquear a todos los usuarios. Debe poder ser simple, opcional o progresivo según tipo de servicio.
```

MUBER hoy:

```text
Inventario es parte fuerte del flujo User, pero ya se detectaron problemas de scroll/avance. Debe mantenerse, pero con UX muy liviana.
```

Recomendación:

```text
Mantener inventario, pero ofrecer modo rápido:
- pocas cosas
- muchas cosas
- subir detalle después
- pedir ayuda asistida
```

---

## 2.11 Chat directo con proveedor

Tendencia:

```text
El chat aparece como muy importante o esencial en varias respuestas.
```

Lectura:

```text
La comunicación con el proveedor reduce incertidumbre.
```

Contraste con MUBER hoy:

```text
Hoy el flujo se ha concentrado en login, User, Driver, tracking, solicitudes y panel director. Falta definir comunicación directa o asistida.
```

Recomendación:

```text
No construir chat completo todavía. Para piloto, usar botón claro de WhatsApp / contacto asistido como solución inicial.
```

---

## 2.12 Pago integrado y seguro

Tendencia:

```text
Pago integrado aparece como muy importante o esencial en la mayoría de respuestas completas.
```

Contraste con MUBER hoy:

```text
WebPay/Transbank está en la ruta del stack, pero debe tratarse con cuidado. Para piloto, puede iniciarse con reserva, pago manual validado o WebPay TEST según madurez del flujo.
```

Riesgo:

```text
No lanzar pago real si el flujo Driver y cierre de viaje aún no están cerrados.
```

---

## 2.13 Calendario y recordatorios

Tendencia:

```text
Aparecen como muy importantes o esenciales en varias respuestas.
```

Lectura:

```text
El usuario necesita acompañamiento de proceso, no solo pedir un camión.
```

MUBER hoy:

```text
Todavía no parece ser prioridad implementada. Puede quedar para etapa posterior al piloto si el flujo base no está cerrado.
```

Decisión recomendada:

```text
No bloquear piloto por recordatorios avanzados. Sí usar mensajes simples de estado y confirmación.
```

---

## 2.14 GPS / seguimiento en tiempo real

Tendencia:

```text
GPS en tiempo real aparece como muy importante o esencial en casi todas las respuestas completas.
```

Contraste con MUBER hoy:

```text
MUBER ya considera tracking y Google Maps como capa logística futura. La ruta de 72 horas define Google Maps para autocompletado, rutas, distancia, tiempo estimado, pricing y tracking visual futuro.
```

Implicación:

```text
Tracking/GPS no es accesorio. Es parte central de la confianza percibida.
```

Recomendación:

```text
Para piloto, aunque no esté Google Maps completo, debe existir un estado visible simple:
- solicitud recibida
- chofer asignado
- en camino
- en carga
- en traslado
- finalizado
```

---

## 2.15 Valoración del proveedor

Probabilidad visible:

```text
1, 3, 4, 4, 5, 5, 5
```

Lectura:

```text
La mayoría de respuestas visibles usaría valoración, aunque hay una respuesta muy baja.
```

Contraste con MUBER hoy:

```text
El flujo Driver ya usa rating como métrica y bono 10%, pero falta cerrar cómo el usuario califica después del servicio.
```

Recomendación:

```text
Agregar evaluación post-servicio como parte del cierre de viaje, no antes.
```

# 3. Contraste con la realidad actual de MUBER

## 3.1 Lo que MUBER ya está haciendo bien

### A. Supabase como backend real

La realidad actual de MUBER está alineada con la necesidad de operación real:

```text
- profiles
- requests
- trips
- drivers
- vehicles
- payments
- inventory_items
- trip_status_history
- driver_applications
```

Esto es correcto para responder a los dolores detectados porque el usuario necesita trazabilidad, estado, seguimiento y confianza.

### B. Mobile-first

La investigación muestra que el usuario necesita resolver rápido desde el celular. MUBER está correctamente orientado a Expo / React Native mobile-first.

### C. Driver y solicitudes entrantes

MUBER ya está trabajando el panel Driver, estado online/offline y solicitudes entrantes/pendientes.

Esto responde a la necesidad operacional real: no basta con que el usuario pida; el chofer debe poder aceptar y operar.

### D. Panel Director

El Panel Director tiene sentido porque el piloto requerirá control manual, validación y monitoreo.

### E. Inventario

El inventario aparece en la investigación como valorado por algunos usuarios y coherente con el diferencial de mudanzas.

MUBER ya lo incorporó, pero debe simplificarse.

---

## 3.2 Brechas críticas entre investigación y MUBER hoy

### Brecha 1 — Continuidad después de aceptar solicitud

Investigación:

```text
El usuario necesita seguridad y seguimiento.
```

MUBER hoy:

```text
En el flujo Driver se detectó que al aceptar una solicitud la tarjeta puede desaparecer y dejar al chofer sin continuidad visible.
```

Riesgo:

```text
Alto. Si el chofer no puede avanzar el viaje, no hay piloto real.
```

Decisión:

```text
Debe existir tarjeta visible de Viaje actual / Servicio en curso después de aceptar.
```

Prioridad:

```text
Crítica antes de piloto.
```

---

### Brecha 2 — GPS/tracking todavía no debe depender de promesa fuerte

Investigación:

```text
GPS en tiempo real aparece como muy importante o esencial.
```

MUBER hoy:

```text
Tracking existe como concepto, pero Google Maps queda como capa futura y todavía se están corrigiendo flujos básicos.
```

Riesgo:

```text
Prometer “GPS en tiempo real” demasiado pronto puede crear expectativa superior al estado real.
```

Decisión:

```text
En campaña pre-piloto usar “seguimiento del estado del servicio” antes que prometer tracking GPS completo, salvo que Google Maps ya esté operativo.
```

Prioridad:

```text
Alta, pero después de estabilizar Driver/User.
```

---

### Brecha 3 — Precio claro aún debe validarse en flujo

Investigación:

```text
Precio, costo por distancia y comparación aparecen como dolores.
```

MUBER hoy:

```text
Hay avances de pricing y tarifas, pero la app debe demostrar claramente cómo llega al precio y qué incluye.
```

Riesgo:

```text
Si el usuario no entiende el precio, no confirma.
```

Decisión:

```text
El resumen de cotización debe separar:
- base
- distancia
- inventario/carga
- asistencia
- extras
- total estimado
```

Prioridad:

```text
Alta antes de campaña.
```

---

### Brecha 4 — Chat/asesor humano no está cerrado

Investigación:

```text
Varios usuarios valoran chat directo y parte de la muestra prefiere contacto humano/tradicional.
```

MUBER hoy:

```text
No hay todavía una solución clara de soporte humano integrada al flujo.
```

Decisión:

```text
Para piloto, no crear chat complejo. Usar CTA visible de WhatsApp o contacto asistido.
```

Prioridad:

```text
Media-alta.
```

---

### Brecha 5 — Inventario puede ser diferencial o fricción

Investigación:

```text
Inventario es valorado por algunos, pero no por todos.
```

MUBER hoy:

```text
Inventario ya existe, pero ha tenido problemas de scroll/avance en móvil.
```

Riesgo:

```text
Si inventario es obligatorio y largo, puede frenar conversión.
```

Decisión:

```text
Crear modo inventario rápido o progresivo.
```

Prioridad:

```text
Alta en test de guerrilla.
```

---

### Brecha 6 — Rating existe para chofer, pero falta cierre con usuario

Investigación:

```text
La valoración del proveedor tiene aceptación visible.
```

MUBER hoy:

```text
Rating ya existe en Driver y bono 10%, pero falta flujo post-servicio para que el usuario califique.
```

Decisión:

```text
Agregar evaluación simple al cierre del viaje.
```

Prioridad:

```text
Media. No antes de cerrar aceptar/avanzar/finalizar viaje.
```

# 5. Implicaciones para la última iteración de investigación

## No repetir preguntas ya respondidas

No conviene volver a preguntar genéricamente:

```text
¿Te gustaría una app de mudanzas?
```

Ya hay señales suficientes para formular preguntas más concretas.

## Preguntas nuevas recomendadas para usuarios

```text
1. ¿Qué información necesitas ver antes de confiar en un chofer?
2. ¿Qué tendría que mostrar MUBER para que confirmes una solicitud?
3. ¿Prefieres precio estimado o precio cerrado?
4. ¿Pagarías una reserva antes del servicio?
5. ¿Qué te da más seguridad: reseñas, foto del chofer, patente, seguro, seguimiento o contacto humano?
6. ¿Te molesta ingresar inventario o prefieres una opción rápida?
7. ¿Usarías WhatsApp para coordinar con asesor MUBER?
8. ¿Qué parte de una mudanza te genera más estrés?
9. ¿Qué servicio usarías primero: flete pequeño, mudanza asistida, última milla o mudanza completa?
10. ¿Qué precio te parece razonable para un flete local corto?
```

## Preguntas nuevas recomendadas para choferes

```text
1. ¿Cuál es tu tarifa mínima por viaje?
2. ¿Qué comisión aceptarías pagar a MUBER?
3. ¿Aceptarías bono por rating 4.9+?
4. ¿Qué datos necesitas antes de aceptar un viaje?
5. ¿Qué zonas evitas?
6. ¿Qué tipo de carga no aceptarías?
7. ¿Cómo prefieres cobrar?
8. ¿Estás dispuesto a entregar documentos y patente?
9. ¿Aceptarías que el cliente te evalúe?
10. ¿Qué haría que te conectes a la app todos los días?
```

# 6. Decisiones recomendadas para MUBER hoy

## Decisión 1 — No lanzar campaña hasta cerrar Driver

Motivo:

```text
Si aceptar solicitud rompe continuidad, no hay piloto operativo.
```

Acción:

```text
Cerrar flujo: solicitud pendiente → aceptada → viaje actual → en curso → finalizado.
```

## Decisión 2 — El mensaje comercial debe centrarse en confianza y precio claro

Mensaje base recomendado:

```text
MUBER: fletes y mudanzas locales con precio claro, chofer validado y seguimiento del servicio.
```

Evitar por ahora:

```text
GPS en tiempo real completo
```

hasta que esté técnicamente validado.

## Decisión 3 — WhatsApp debe ser puente de confianza

No crear chat avanzado todavía.

Para piloto:

```text
Botón: Hablar con asesor MUBER por WhatsApp
```

## Decisión 4 — Inventario debe tener modo rápido

No todos valoran inventario igual.

Recomendación:

```text
- Inventario rápido
- Inventario detallado
- Necesito ayuda para inventario
```

## Decisión 5 — Rating/bono sirve para operación de choferes, pero falta cliente

Mantener bono 10% para chofer.

Agregar después:

```text
Califica el servicio
1 a 5 estrellas
Comentario opcional
```

# 7. Backlog pre-piloto derivado del análisis

## Crítico

```text
1. Driver: no perder tarjeta al aceptar solicitud.
2. Driver: mostrar Viaje actual / Servicio en curso.
3. User: confirmar que cotización se entiende.
4. User: asegurar scroll y avance en inventario.
5. Panel Director: monitorear solicitud/viaje.
```

## Alto

```text
6. Mostrar confianza del chofer al cliente.
7. Definir estados visibles del servicio.
8. Agregar contacto WhatsApp / asesor humano.
9. Simplificar inventario con modo rápido.
10. Preparar test de guerrilla sobre cotización, inventario y confirmación.
```

## Medio

```text
11. Rating post-servicio.
12. Recordatorios simples.
13. Mensajes de campaña.
14. Benchmark accionable.
15. Journey map actualizado.
```

## Futuro cercano

```text
16. Google Maps Places/Routes.
17. WebPay TEST.
18. EAS Build.
19. Edge Functions para acciones sensibles.
20. RLS completa antes de piloto real.
```

# 8. Conclusión

La investigación inicial confirma que MUBER está bien orientado, pero también muestra que el piloto no debe vender solo “mudanzas por app”.

La propuesta debe ser:

```text
menos estrés
precio claro
chofer validado
seguimiento
contacto humano si hace falta
```

MUBER hoy ya tiene una base alineada:

```text
- Expo / React Native mobile-first
- Supabase backend real
- User
- Assisted
- Driver
- Panel Director
- solicitudes
- viajes
- tracking conceptual
- rating/bono chofer
```

Pero antes del piloto real/comercial debe cerrar brechas críticas:

```text
1. continuidad del viaje después de aceptar solicitud
2. cotización clara y entendible
3. inventario sin fricción
4. confianza visible para el cliente
5. soporte humano inicial vía WhatsApp o asesor
6. estados del servicio claros
```

Decisión final:

```text
La investigación antigua valida la dirección estratégica de MUBER.
La realidad actual de MUBER valida que el stack y flujo van bien.
La última iteración debe enfocarse en cerrar confianza, continuidad operacional y claridad de precio antes de campaña.
```
